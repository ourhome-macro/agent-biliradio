# Agent 与 Feed 平台的核心难点判断

日期：2026-10-19。依据当前工作区实现做工程判断；包含未提交代码，不代表线上部署验收。本次只新增分析文档，未修改实现，未重跑测试。长任务与 trace 的实现依据见 [专项核查](long-task-and-trace-review-2026-10-19.md)。

## 核心判断

如果各选一个最难的问题：

- Agent：在任务变更、上下文压缩和故障恢复之后，仍根据当前有效意图，安全地接着完成任务。
- Feed：在分页、缓存、搜索索引、互动投影和媒体资产异步变化时，持续返回当前有权限、业务上合适且能播放的内容。

这两个问题分别要求定义任务执行语义和在线内容交付语义。LangGraph、Kafka、Redis、ES 等组件各自解决部分机制，最终是否正确仍要由业务状态与边界条件定义。

## Agent：最难的是恢复后的执行仍然正确

### 1. 分清“已执行”和“已知道结果”

最危险的窗口是外部副作用已经发生，而工具 succeeded 流水尚未提交。重放可能重复操作，跳过又可能丢掉实际未完成的操作。数据库 checkpoint 只能保存系统已知的事实，不能证明未知的外部结果。

当前工具流水支持稳定 call_id、成功结果复用、幂等重试、非幂等未知结果对账；同步线程超时仍可能继续执行，所以即使宣称幂等，也会避免立即重叠重试。这比实现图节点跳转难得多。

生产验收应围绕副作用前后、流水提交前后、租约切换前后注入故障，证明已提交阶段不重复，未知结果被明确阻断，旧 owner 不能继续提交有效结果。当前 run 租约没有覆盖所有 checkpoint/tool 状态提交，仍有加强空间。

### 2. 跨压缩保留当前有效意图

长期偏好、当前请求、原始任务和后续修订可能相互矛盾。例如长期不喜欢 Rap，本轮明确想听 Rap，随后又要求排除某位歌手。这要求记忆检索与任务约束各有明确的优先级，旧摘要不能把已撤销限制重新带回来。

当前 context_window 保存原始任务、当前意图、有效约束版本及摘要，并按完整 tool 消息组压缩。难点在于判断约束是否真的被替换、哪些证据必须保留，以及压缩后的决策是否保持一致。关键词和主题匹配有适用范围，不能当作完整自然语言约束推理。

### 3. 证明“完成”满足业务要求

图走到 finish、模型返回可解析 JSON、工具没有抛异常，都只是执行层面的成功。推荐还要满足语言、风格、排除项、可用性和证据来源；长期记忆还要避免把一次请求或错误推断永久化。

因此成功判据需要由业务校验、任务结果及来源共同确定。trace 用于定位与评测；不应把模型自述完成或 trace 的 completed 字段单独作为任务正确性的证明。

## Feed：最难的是异步系统下的正确、连续交付

### 1. 固定分页和即时撤销之间的冲突

用户需要稳定的翻页结果，同时下架、公开改私有、取消关注和“不喜欢”必须及时影响返回。旧页、Redis 缓存、ES 搜索结果都可能仍然包含内容 ID；清缓存也不能可靠地覆盖并发请求和所有派生读模型。

当前 Feed 固定已发页面的 ID 与顺序，render 时重新读取权威状态、ResourcePolicy、当前 reaction 和关注范围，并压制不允许返回的条目。页稳定性和最新权限采用不同的判断时点。这是重要设计，但不能据此宣称已经签发的对象存储 URL 可以即时撤销。

### 2. 外部内容进入平台后的媒体生命周期

本项目需要从外部内容源解析、获取音视频，生成 HLS，处理冷启动播放、完整性校验、上传、重试、签名刷新、容量限制及无人观看取消。目录中存在内容和存在可播放媒体是两种状态。

代码中的复杂度集中在：asset 与 content 分离；多个 playback 共用 import；媒体租约与运输任务租约校验；获取完成后复用本地源，只重试上传；manifest 最后上传；数据库发布 ready 前检查完整源和内容状态。用户快速划走时还要平衡取消无用下载与保留可能复用的资产。

我的判断是：这是当前 Feed 实现里复杂度最集中的链路，也是需要优先通过实测证明体验的地方。首片段耗时、首帧时间、卡顿、冷任务排队和资源成本应分别观测，API 延迟不能替代播放体验。

### 3. 重复与乱序事件下维护可重建读模型

点赞 → 取消 → 点赞可能快速发生，事件会重复和乱序。直接收到一次事件就增减计数容易漂移，也容易让旧状态覆盖新状态。

当前 reaction 用关系 version、Inbox 和 projection 记录已贡献状态，仅更高版本更新贡献差值；SQL 提交后向 Redis 发布绝对值及版本。搜索和缓存也有独立异步消费者。这些设计的核心是业务事实可重建、旧版本不能回滚新版本，以及错误能够对账，而非仅仅成功消费消息。

## 两边共同的产品难点：反馈是否代表真实偏好

用户很快划走一条内容，可能因为内容不喜欢，也可能因为首帧太慢、播放失败、已经看过或当时场景不合适。Feed 产生行为，推荐策略解释行为，Agent/AMEM 又可能把解释沉淀成长记忆；一旦混淆原因，就会形成错误反馈循环。

当前有短期反馈重排、去重和有界探索实现，但不能据此认定用户收益已得到因果验证。播放质量信号、负面偏好信号和曝光上下文应区分；明确反馈和推断反馈应有不同置信度与有效期，用户本轮要求应优先。评测需要同时验证推荐满足约束、可播放性、重复率、负反馈和用户收益。

## 当前最值得投入的顺序

1. Agent：先补恢复与副作用协议的闭环，包含跨 owner 提交隔离、job/tool 对账协同以及明确的业务完成判据；多机部署前统一持久化状态。
2. Feed：先验证媒体冷启动到连续播放及权限撤销链路，再按实测瓶颈优化缓存、预取、供给与排名。
3. 联合评测：把播放故障和用户偏好区分开，避免噪声进入长期记忆；在有曝光与质量上下文的前提下验证推荐改动。

这些排序是结合当前代码的判断，不是性能瓶颈测量结果。本次没有运行线上流量测试、故障注入或用户实验。
