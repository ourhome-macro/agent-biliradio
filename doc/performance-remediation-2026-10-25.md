# 容量修复与对照验证

日期：2026-10-25。按授权顺序处理 Feed 批量读、代理授权前限流、点赞写锁与 SQL、Kafka 消费调度。基线见[容量报告](performance-results-2026-10-25.md)。不调整旧测试门槛，不以取消授权或幂等校验换取吞吐。

## 1. Feed 批量读

已实现：授权批量查询同时读取媒体、当前互动与计数，渲染复用同一批 SQL 行，移除逐卡 JOIN；关注作者按页批量读取并判断集合交集。已有的 SQL 互动/计数直接用于响应，不再额外读 Redis 或查询 Bitmap 用户映射；Bitmap 和计数投影仍保留。内部原始行不等于授权；最终卡片仍依据当前授权结果、状态和用户互动判断是否抑制。新增普通热页面最多 3 个 SELECT 及缓存命中后转私有的回归。

## 2. 代理授权前限流

已接入：独立的每进程 16 路非阻塞授权预算，在播放创建、描述符、心跳、释放、分片读取前取得；ASGI 字节路由在身份 SQL 前取得同一预算，跨线程通过 ContextVar 保持嵌套调用可重入。预算小于数据库池上限 20，返回流描述符时释放授权槽，字节传输继续使用原 32 路出口预算。过载明确返回 503，不扩大数据库池，不缓存或跳过授权。初轮 8 路预算已保护 SQL 池，但突发拒绝过多，最终按 16 路重新对照接受量与延迟。

## 3. 点赞写锁与 SQL

已实现：Bitmap 用户映射先无锁读取，只在首次分配时加锁并复查。没有 track 的 UGC 写命令不再争抢全内容写锁，也不查询必为空的 track 别名；视频仍保留与别名准入共享的 track 锁。投影继续保留与在线 rebuild 共享的全内容锁，避免重建与增量更新并发导致计数漂移；没有为吞吐拆掉该语义。计数行由内容创建事务保证，不再对已存在行执行 INSERT IGNORE 后升级写锁。命令幂等、版本单调及视频别名一致性保留。

## 4. Kafka 消费调度

已实现：每分区仍只保持一个在途任务，仅合并同轮已经持久完成且仍持有 assignment 的 offset，以一次同步 commit 提交。提交失败保留完成结果，不重跑已成功 handler；提交期间丢失 assignment 时不恢复旧分区。存在在途任务时将 poll 上限缩短为 10ms，空闲保持原预算，避免暂停分区让已完成任务等待 100ms。待 offset 失败/撤销回归和真实 Kafka 对照。

## 同负载结果

对照基线为[上一轮原始结果](performance-results-2026-10-25.json)，当前[对照快照](performance-remediation-2026-10-25.json)保留前后数据和 SHA-256 回执。`scripts/compare_capacity_remediation.py` 从原始行重算 21,888 条请求的状态计数及 P99。当前仍是 Windows 单实例、MySQL 64 MiB buffer pool 的短时探索，不是上线容量认证。

### Feed

普通热页实测固定 3 次 SELECT（会话、固定页、批量授权/渲染），从原约 14 次下降，依赖资源额外授权仍会增加批次。已拿到的互动/计数直接复用 SQL 快照，未减少权限校验。

成功从 819 增为 2241，成功响应业务状态检查未发现错误；最终 likes=285、dislikes=100，与关系表重算一致，HTTP/Flask 静默、pending=0。

但收敛时间从 **4.44 秒增至 31.31 秒**。前台接收更多事件后，2 个投影 worker 成为明显瓶颈，因此不能只报告吞吐改善。第一档成功 SQL 执行累计耗时中，锁类约 11.84 秒、任务类约 5.47 秒、映射约 4.88 秒；这些为并发 driver wall time，不能当作单请求延迟或 MySQL CPU 时间。后续应优化任务领取/投影批处理，并继续维护 rebuild 的互斥语义。

### Kafka

相同 208 条任务、目标 2/10/40/s、3 分区与 2 线程：峰值 lag **166→141**，恢复 **30.81→27.28 秒**，整体消费 **4.92→5.37/s**，最终 lag=0、208/208 完成。10/s 档末 lag 从 19 降至 0，40/s 仍积压。

改进约一成，不能声称数量级提升。任务 SQL、逐任务事务和同步提交仍值得进一步 profiling；未通过放宽 offset、并行处理同一分区或省略 Inbox 来提高指标。
