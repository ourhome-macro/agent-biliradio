# Feed 热点主动刷新设计

日期：2026-10-25。生命周期设计已实现，功能默认关闭；实测结论、开关和边界见[实现与验证](feed-hotkey-validation.md)。本文保留设计目标，具体实现参数以验证文档和源码为准。

## 结论与适用范围

采用“统计访问 → 晋升热点 → 到期前刷新 → 热度下降 → 停止刷新”的生命周期合理。该机制是热点主动刷新，不是仅延长旧值 TTL。首期仅覆盖公开内容 Metadata；不覆盖私人元数据、Feed 页面、互动状态、签名 URL 或执行租约。

当前内容缓存默认 soft=60 秒、hard=300 秒并对硬寿命做 0.8～1.0 抖动，不是物理 TTL=60 秒。新策略应明确普通软期限、硬期限、热点刷新提前量，不能把示例数值直接视为现行配置。

## 生命周期

1. 普通状态：沿用现有请求触发的缓存读写和软失效刷新，记录公开内容的授权读取热度。
2. 识别热点：以逻辑 content ID 聚合全部 API 进程的访问量；在本地缓存返回前计数，避免本地命中掩盖热点。计数只反映需求，不算用户偏好，也不采用客户端自报热度。
3. 热点晋升：最近 60 秒访问超过晋升阈值，并满足热点容量预算后进入热点注册表。注册表保存近期热度、最后访问时间、连续冷窗口数与下次刷新时间，禁止持久化请求闭包。
4. 提前刷新：调度器取到期任务，由带所有者 token 的租约控制同一内容刷新。worker 根据 content ID 重新查当前 SQL 内容、版本、权限和状态，只向当前公开版本 key 发布新数据，并同时重设 soft_at、hard_at 与 Redis TTL。
5. 热度下降：降级阈值低于晋升阈值，连续多个完整窗口低于降级阈值后退出。判定热度使用真实请求计数，后台刷新不能给自己增加热度。
6. 退出热点：停止主动调度，保留当前缓存按既有期限自然到期。后续访问回到普通请求刷新路径；不因降级立即删除可用缓存。

用于讨论的起始参数可设为晋升 600 次/60 秒、降级低于 120 次/60 秒并持续 3 个窗口；这些不是压测结论，必须按真实流量、数据库成本和刷新预算调整。滚动窗口可用固定数量的短时间桶聚合，避免维护无限访问明细。

若采用物理 TTL=60 秒的独立示例：t=0 写入，t=20 达到晋升条件，注册下一次刷新约 t=45～50；刷新成功后从完成时刻重新计算有效期。未晋升前已发生 miss 的请求仍需普通回源保护，晋升不能倒推消除之前的失效。

## 生产约束

- 热度采集在进程内聚合后批量上报，并给本地计数器、时间桶和热点集合设置容量上限与清理策略；需明确允许的进程退出计数损失和上报延迟，避免每次本地命中都同步写 Redis。
- 调度需要原子认领、超时重领和持久到期时间；可使用 Redis 有序集合管理 due time，但不能仅删除任务后提交进程内线程池，否则进程退出会丢调度。
- 刷新并发、每秒回源量和热点数均受限，刷新时间加抖动；Redis/数据库故障时退避，不能绕过保护无限回源。超过容量时按热度和预期收益保留热点。
- 当前刷新锁固定 5 秒且无续租。新 worker 应采用有上限的执行时间、token 校验续租以及发布时的租约所有权校验；失去租约的旧 worker 不可发布或覆盖新调度状态。
- 当前 Feed loader 捕获请求已经查到的 SQL row，只解析 metadata_json。后台定时刷新必须新增按 ID 重新读取的 loader，不能反复使用旧 row 延长缓存。
- 内容版本和权限版本继续进入 key；私有化、删除或下架后停止主动刷新。缓存不授予访问权限，读端仍核对当前 SQL 权限；事件删除与后台刷新竞争时，旧版本 key 即使残留也不可被当前版本读取。
- 发布失败不得延长数据新鲜度，保留既有硬截止时间。硬期限到达后不能无限提供旧数据；后续请求按受限回源规则处理。
- 优先消除 `_render` 中逐卡完整 JOIN、复用批量授权与版本查询；否则额外后台刷新只增加数据库工作，不能自动证明降低主库压力。

## 验收不变量

- 本地缓存命中也计入热度；跨进程累计可以晋升；刷新任务不增加访问计数。
- 重复调度不造成无界重复回源；进程崩溃后任务可恢复；过期租约持有者不能发布。
- 临界热度不反复升降；热点容量与刷新并发严格有界；降级后停止主动刷新。
- 更新、私有化和删除与刷新并发时，当前用户看不到未授权或旧版本内容。
- 刷新失败不延长原有硬期限；Redis 故障恢复不会触发集中回源；Feed 会话不被续期。
- 使用独立 Redis、隔离业务库和固定时钟测试生命周期，再比较 SQL 次数、L1/L2 命中率、刷新 QPS、回源峰值与 P95。没有测量结果前不报告性能收益。
