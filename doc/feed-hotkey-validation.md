# Feed 热点探测与主动刷新验证

日期：2026-10-25。代码已实现，默认关闭；未修改运行中业务配置，未部署或新增发布流程。历史设计见[生命周期方案](feed-hotkey-design.md)。

## 已实现行为

- Feed 仅在当前请求通过权限校验后，把公开内容 ID 传给缓存计数；在本地命中返回前记录。私人内容、页面、计数投影、后台刷新不增加热度。
- 每进程在内存累计，默认每秒批量上报，单批最多 256 个 ID。Redis 使用服务器时间维护 6 个 10 秒桶，窗口为当前桶及之前 5 桶，覆盖约 50～60 秒，不是精确滑动 60 秒。
- 同一数据库命名空间下跨进程聚合；默认达到 600 次晋升，低于 120 次时按分钟评估，连续 3 次低热度退出。同一评估窗口不会重复增加冷窗口数；停机错过的窗口不会虚构为已观测的低热度。
- 默认最多跟踪 2048 个内容、保持 256 个热点；满额不再接纳新 ID，记录丢弃指标，不承诺高基数饱和时准确找出所有热门内容。计数器、桶、批次、热点表和执行池均有容量上限。
- 热点通过 Redis 有序集合记录到期时间，约每 40.5～45 秒刷新，保留调度抖动。任务认领与租约原子写入，活跃执行租约在同一命名空间内最多 2 个；每进程也最多执行 2 个任务。
- 刷新 worker 只捕获数据库标识，不保留用户请求或旧 SQL row。重新通过 `ResourcePolicy` 查询当前公开权限、UGC 发布与来源权限、内容版本，再发布对应版本 key；读端继续核对当前 SQL 权限。
- 刷新写入新的数据、soft_at、hard_at 及 TTL，硬寿命同样采用 0.8～1.0 抖动。新机制不改变普通请求缓存的 60 秒软期限与 240～300 秒硬寿命。
- 独立热点租约默认 10 秒，校验 token 续期，发布时再次校验持有者；失去租约、被失效事件清理、超过 5 秒发布预算时不发布。旧普通请求 loader 的 5 秒锁保持原有机制。
- 失败重试有退避；失败不延长旧缓存期限。worker 退出后租约到期可接管；API 创建热点管理器时即开始扫描历史调度，无需该 ID 再被读取。
- 热点管理器使用弱引用并随缓存关闭，避免资源缓存淘汰后残留主动刷新线程。

计数是可丢失的优化遥测：Redis 故障、进程退出或缓冲容量不足会丢部分计数，故障积压不会被重放成当前热度。Redis 恢复后从新访问重新累计。状态和缓存都不作为授权依据。

5 秒限制是发布预算，不会强制终止正在执行的 SQL。数据库仍受现有连接与语句超时约束；租约过期的慢任务可能继续占用本进程执行槽，不能把“2 个活跃租约”宣称为任何故障下全局最多 2 个物理 SQL。该边界必须在部署环境结合 MySQL 慢查询验证。

## 配置与观测

在业务环境显式配置后重启对应 API 进程：

```dotenv
FEED_HOTKEY_ENABLED=true
FEED_HOTKEY_PROMOTE=600
FEED_HOTKEY_DEMOTE=120
FEED_HOTKEY_CAPACITY=256
```

默认仍为 false。阈值必须满足 `0 < demote < promote`，容量不超过跟踪上限。时间窗口、调度参数与执行上限定义在 `HotKeyConfig`，测试使用压缩参数，不会改变生产默认值。

Feed health 增加 `hotkeys` 状态，包含开关、Redis 可用性、热点数、跟踪数、租约记录数及本地待上报 ID 数；租约记录数可能包含尚未清理的过期记录。Prometheus 使用 `radio_feed_operations_total{operation="hotkey",outcome="..."}`，可观察晋升、降级、刷新成功/失败、发布被拒绝、超时、容量丢弃和后台 tick 异常，不把内容 ID 用作指标标签。

## 隔离验证方法

```powershell
py -3.12 scripts/validate_hotkeys.py
py -3.12 scripts/quality.py test
py -3.12 scripts/quality.py lint
```

验证入口通过质量脚本创建隔离环境，禁止 dotenv 加载，清空业务数据库及凭据配置；启动随机 loopback 端口、临时数据目录的原生 Redis，不连接已有 Redis。输出在 `artifacts/quality/hotkey-ab.json` 与 `hotkey-regression.xml`；已保留本次 [A/B 原始数据](feed-hotkey-ab-2026-10-25.json)供 GitHub 复核。

回归覆盖本地命中计数、跨实例汇总、双阈值退出、容量限制、全局租约预算、旧 owner 发布拦截、失败不延期、任务接管、失效竞争、新版本与私有化、Redis 故障、慢任务拒绝发布、后台刷新和资源关闭。真实故障注入会终止已认领任务的子进程、终止独立 Redis，再从其 AOF 重启验证调度恢复；重启测试显式使用 `appendfsync=always`，不据此承诺默认 everysec 配置零丢失。

A/B 是缓存层受控负载对照：A 为现有请求触发刷新，B 增加热点机制。两组使用相同固定随机种子、请求计划、90% 热点访问、缓存期限、两个缓存实例及 8ms 模拟源读取耗时；压缩时间参数并相应缩短 L1，覆盖多个生命周期。240 请求/秒跑 3 对，交替执行顺序；1200 请求/秒另跑 1 对。记录请求错误、前台路径加载、主动加载、总加载、服务延迟和包含排队时间的响应延迟。

这里的加载次数不是完整 Feed 的 SQL 次数：现有 `_render` 仍执行逐卡 SQL；A/B 不包含 HTTP、真实 MySQL 容量或推荐质量，也不是线上用户随机分流实验。性能结果仅用于判断该缓存机制是否值得默认开启。

## 实测结果

最终单独运行共 25,920 次请求，错误为 0；没有与全量测试同时执行。下表 240 档为 3 个种子的累计加载数与各轮 P95 的算术均值，并非合并请求后的 P95；1200 档只有 1 对样本。

| 提供负载 | 组别 | 请求数 | 前台路径加载 | 主动加载 | 总加载 | 服务 P95 ms |
| --- | --- | --- | --- | --- | --- | --- |
| 240/s | A 原有机制 | 5760 | 297 | 0 | 297 | 1.357 |
| 240/s | B 热点机制 | 5760 | 265 | 48 | 313 | 1.314 |
| 1200/s | A 原有机制 | 7200 | 101 | 0 | 101 | 1.203 |
| 1200/s | B 热点机制 | 7200 | 87 | 23 | 110 | 0.876 |

240 档前台路径加载减少 10.8%，但总加载增加 5.4%；1200 档分别减少 13.9%、增加 8.9%。240 档各轮 P95 有改善也有退化，不能把均值差异判定为稳定收益；1200 档单对样本只能视为一次观测。原有软失效机制已经可异步刷新，新增主动刷新更多是在提前安排加载，并不天然减少总回源。

结论：功能与故障边界已验证，默认保持关闭，未证明整个 Feed 性能或业务数据库负载得到改善。优先解决逐卡 SQL，再用真实隔离 MySQL/HTTP 工作负载判断是否开启，不修改阈值或缓存期限来人为制造 A/B 胜出。

定向回归最终 46 项通过；实际 worker 终止后可接管，旧 token 不可发布，独立 Redis 故障时普通读取可有限回源，AOF 重启后可恢复调度。最终 `quality.py test` 为 318 passed、59 deselected，耗时 88.98 秒；`quality.py lint` 通过。59 项为非集成入口排除的集成用例，未运行完整 MySQL/Kafka/ES 等基础设施验收，不宣称这些用例通过。
