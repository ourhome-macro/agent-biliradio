# 容量实验结果：2026-10-25

全部模块和五组 A/B 都已执行；当前基线暴露出 P0 容量问题，不能标记为生产容量验收通过。[A/B 详情](performance-ab-2026-10-25.md)、[原始汇总与校验回执](performance-results-2026-10-25.json)、[方法和入口](performance-experiments.md)。

## 环境与可信边界

- Windows 11、Python 3.12.5、16 个逻辑 CPU。独立原生 MySQL，buffer pool 64 MiB；独立 Redis/MinIO；Kafka 为独立单 broker 容器，2 CPU/1 GiB、3 分区、2 消费线程。没有复用业务数据库、API key 或私人账号。
- 点赞/Feed 使用实际 Flask blueprint，经 uvicorn＋a2wsgi、16 个 WSGI worker，注入测试身份，不包含 OIDC/CSRF 成本。流代理使用生产 ProxyMediaService、真实 MySQL 授权和 HTTP 夹具，不是 256 个真实浏览器解码器。
- 延迟从计划到达时刻计算，包含排队和调度；服务超时为 5 秒。生成器最多 256 个在途请求，满额后的丢弃单独列出，绝不把这些请求算成零延迟成功。未达目标发送量时，不推断服务已承受目标 RPS。
- 已从原始行独立重算 **30,460 条 HTTP 请求**与 **3,396 条代理请求**的分位数和状态计数，并重算 Kafka lag 及 100 个画像排序查询的 nDCG。初轮 smoke 的生成器启动追赶和冷初始化不用于 A/B 结论；正式 A/B 统一预热 SQL 目录，3 个固定种子、交替执行顺序。

## P0：点赞计数

每档计划 4 秒，512 个测试用户对同一公开音频元数据夹具变更 like/dislike/neutral，不在此模块读取音频字节或测量发布准入。后台为 2 个实际 SQL 投影 worker，写入 Inbox、绝对计数及 Redis Bitmap；Kafka 吞吐和音频字节处理独立测量。

| 目标 RPS | 计划请求 | 成功 / 503 / 超时 | 生成器丢弃 | P95 / P99 ms | 确认成功吞吐 req/s |
| --- | --- | --- | --- | --- | --- |
| 200 | 800 | 202 / 32 / 172 | 394 | 5058.8 / 5072.3 | 22.5 |
| 500 | 2000 | 188 / 34 / 162 | 1616 | 5112.8 / 5145.1 | 21.0 |
| 1000 | 4000 | 214 / 28 / 143 | 3615 | 5409.4 / 5513.1 | 24.2 |
| 2000 | 8000 | 215 / 50 / 119 | 7616 | 5514.2 / 5561.6 | 24.5 |

P95/P99 覆盖已发出的成功、503 和超时请求，不含根本没有发出的生成器丢弃。成功吞吐以阶段实际耗时（含等待响应）为分母，不是稳态峰值。

819 个确认成功响应的业务状态检查为 **819/819**，不代表 14,800 个计划请求全部成功。停止生产后约 **4.44 秒**，HTTP/Flask 请求和投影队列均静默；实际 likes=202、dislikes=91，与关系表独立重算一致，pending=0。超时可能已经提交，不能据超时回滚或推断失败。

结论：一致性检查通过，容量不通过。该单实例夹具在 200 RPS 的第一档就已超载；应优先分析热门内容写锁、用户 Bitmap 首次分配、每命令 SQL 与排队，而不是宣称可承受 2000 RPS。

## P0：流代理

模拟播放器执行初始 Range、跳转、取消读取和切换，包含心跳与释放。受控源解析耗时 20ms，上游每 4KiB 延迟 2ms，使用真实 FFmpeg fMP4 文件；吞吐是此工作负载有效载荷，不是公网出口带宽上限。

| 并发播放器 | 206 / 500 / 503 / 410 | TTFB P99 ms | 出口 MiB/s | 采样峰值 RSS MiB | 最终槽位与上游连接回收 |
| --- | --- | --- | --- | --- | --- |
| 16 | 96 / 0 / 0 / 0 | 802.3 | 1.55 | 105.1 | 是 |
| 32 | 192 / 0 / 0 / 0 | 1401.7 | 1.26 | 119.5 | 是 |
| 64 | 384 / 0 / 0 / 0 | 4205.2 | 1.03 | 122.5 | 是 |
| 128 | 617 / 79 / 0 / 0 | 6784.8 | 0.85 | 127.4 | 是 |
| 256 | 675 / 361 / 31 / 1 | 9485.3 | 0.70 | 132.4 | 是 |

RSS 为 0.2 秒采样峰值，进程只承载服务和受控源，生成器独立进程。配额最终回到 32，源连接归零，短测未发现逻辑连接泄漏；这不等于长时间 FD/句柄稳定性已经验收。

128/256 路明确出现 SQLAlchemy QueuePool 超时，现有池为 10＋10、等待 3 秒。HTTP 夹具将未归一化异常记录为 500；真实 ASGI 流路由会把该类异常返回 503，因此不能把夹具 500 数直接宣称为生产 500 数。关键问题相同：读取当前授权发生在字节代理配额之前，数据库先受压，32 路出口配额没有保护授权查询。

## P1：Kafka、上传、推荐

- **Kafka**：目标 2/10/40 条每秒，阶段确认速率约 2.27/10.20/40.16/s（首条在 t=0、阶段仅约 4 秒），档末 lag 为 0/19/165，峰值 166；停产后 **30.81 秒**恢复到 lag=0，208/208 个唯一任务完成，整体消费约 4.92/s。业务 handler 固定耗时 20ms，不含真实 AMEM。初轮更强压力 600 条任务在 90 秒恢复预算后仍有 lag=30，保留为失败边界，不算通过。消费循环逐分区暂停、逐条同步提交及持久任务 SQL 应进一步剖析。
- **UGC**：有效静音 WAV，64KiB/1MiB/8MiB/32MiB。并发 1/4/8，样本 4/8/16，上传成功率均 100%；上传 P95 为 109/109/172ms，SQL 确认 P95 为 31/63/156ms，ready P95 为 641/828/1609ms。这里确认是实际服务方法，不包含 HTTP 包装。15 秒真实测试签名到期后清理，临时对象残留为 0/28；不是生产默认 15 分钟生命周期和复杂音频集的全面验收。
- **AMEM 画像**：生产 ProfileProjector＋RecommendationEngine，在 100 个固定、刻意易判的合成偏好查询上，nDCG@8 为 **0.3114 → 1.0000**。偏好和标签由夹具给定，因此只能证明画像输入影响排序，不能证明记忆提取质量或真实推荐效果。CTR、完播率均未测，未用模拟点击填充。

## 下一步优先级

1. P0：在代理授权查询之前限制并发，压缩权限/资产读取，避免 SQL 池先耗尽；保留实时授权，不能以跳过校验换吞吐。
2. P0：Feed 批量读取并复用授权行；对点赞写锁、首次用户映射、投影排队分别 profiling。保持幂等与计数不变量。
3. 保留 Singleflight 和本地公共元数据缓存；HotKey 主动刷新继续默认关闭。PlayURL 缓存可减少解析调用，但目前端到端延迟被 SQL 成本掩盖。
4. P1：Kafka 需要单独评估安全批量提交与 poll 调度；AMEM 上线 A/B 应先核对真实 treatment 是否读到画像，再采集随机用户级曝光/点击/有效观看。Feed 自动播放不能冒充推荐卡点击。
