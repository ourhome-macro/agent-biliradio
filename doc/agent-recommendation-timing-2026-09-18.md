# 音乐助手推荐全链路时长采样（2026-09-18）

## 口径

本地 Radio/AMEM，提示词“给我推荐一些唱跳舞台”，浏览器 Edge；起点为点击“发送”，终点为当前页推荐卡显示 8 首歌曲并标记 `completed`。后端使用持久任务、业务 trace 和 SSE 事件时间；单次样本，不代表不同 B 站源站或冷/热缓存状态的百分位数。原始数据位于本地忽略目录 `recommend-radio/server-data/timing-review/agent-timing.json`。

后端推荐计算 trace 为 **0.60 秒**：候选池读取 122ms，场景记忆读取 21ms，画像投影 0.62ms，打分 0.30ms，重排 2.76ms，曝光写入 128ms。发现任务为 **29.46 秒**，其中候选文本向量持久化 **20.40 秒**，约占发现任务 69%；队列等待 1.12 秒，B 站搜索/来源补充与准入占其余时间。

## 推送延迟定位

第一轮 `recommendation` 进度事件入 outbox 后约 **31.1 秒**才写到 SSE 网关；初始 `session` 事件约 **30.8 秒**，`done` 事件在报告结束后才被送达。前端凭持久任务/发现状态校对在 13.12 秒显示初始卡、43.35 秒显示完整卡，因此本轮没有被延迟的 SSE 卡住。

根因是同一 SSE lane 的多条 durable job 原先被 outbox 一次发布到两个 Celery worker，后发任务若先被认领会因前序任务仍排队而退出，接下来等 30 秒重投。已改为 outbox 每个 lane 只发布队头；每条 SSE job 完成后立即尝试投递下一条。同 lane 仍保持顺序，其他用户/会话可并行。

## 第二轮实测（修复 SSE 队列发布顺序后）

第二轮提示词为“给我推荐一些现场舞台”，同一套本地环境，但候选与缓存不同；两轮总耗时不能作为 A/B 性能比较。

| 阶段 | 点击后的时间 / 阶段耗时 |
| --- | ---: |

| 对话任务完成 | 12.26 秒 |
| 初始推荐卡在页面出现（5 首） | 12.66 秒 |
| 发现任务入队 | 11.02 秒 |

第二轮推荐计算 trace 为 **0.95 秒**。发现任务中队列等待 **4.08 秒**，候选文本向量持久化 **29.49 秒**，约占发现任务 70%。终态 `session` 事件从 outbox 入队到处理完成约 **0.52 秒**，`done` 事件约 **0.70 秒**；浏览器收到终态卡片后约 **31ms** 完成可见渲染。前序 `task` 事件仍有约 6.15 秒的排队/处理耗时，说明队列负载与出站分发仍会影响首个进度提示。

因此本轮的主要瓶颈是发现阶段的同步向量生成与持久化。若要继续压缩完整卡时长，应在保持候选准入与追踪可审计的前提下，把非必要的向量补建移出首次可见结果的关键路径。
